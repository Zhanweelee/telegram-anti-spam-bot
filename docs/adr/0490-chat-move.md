# ADR 0490：群升级后沿用原来的设置

- 状态：已接受
- 日期：2026-11-05

## 背景

普通群升级成超级群时，Telegram 更换 `chat.id`。旧群收到 `migrate_to_chat_id`。新超级群收到 `migrate_from_chat_id`。开关、关键词、洪泛、重复、禁言时长、验证、允许的主机名和白名单都按群编号存放。编号一变，这些设置就像没配过。

这两条服务消息的正文是空的。编号本身不是垃圾文本。

## 决策

- `migrate_to_chat_id` 是非 0 的安全整数，且和当前群不同时，事件带 `chatMove`。`from` 是当前群，`to` 是新编号。否则 `migrate_from_chat_id` 满足同样条件时，`from` 是旧编号，`to` 是当前群。同时出现时先认 `migrate_to_chat_id`。编号不进正文。
- 0、小数、字符串、布尔值和与当前群相同的编号不带 `chatMove`。
- 审核这条事件之前，把 `from` 上已经保存、而 `to` 还没有的设置抄过去。包括 dry-run、规则开关、规则处置、上报编号、洪泛、关键词、重复、禁言时长、验证时长、验证失败处置、允许的主机名和白名单。新编号已经有的那一项留下。旧编号上的设置留下。
- 抄写失败时记 `chat_move_failed`，这条消息仍按原规则审核。抄到至少一项时记 `chat_moved`，只带事件编号、当前群编号和抄了几项。
- 不删除这两条服务消息，也不新增检测器。没有新命令。菜单仍是 99 条。
- 警告次数、入群验证进度、审计、额度和 `chats.json` 整份替换不跟着搬。30 天保留期不动。

## 备选

| 方案 | 放弃原因 |
| --- | --- |
| 只删掉升级提示 | 设置仍停在旧编号。后面的消息会按默认规则走。 |
| 覆盖新编号上已经保存的设置 | 管理员可能已经在新群里改过。后来的升级消息不应把它改回去。 |
| 连警告次数和审计一起搬 | 次数和审计是历史。搬动会把两段记录合成一段，也可能把未完成的验证带到另一个群。 |
| 新命令 `/move` | 升级消息自己已经带了两个编号。菜单只剩一个空位。 |

## 后果

- 升级之后，新超级群沿用旧群已经打开的规则、追加的关键词和白名单。新群里已经写过的那一项不变。
- `chats.json` 整份替换仍按编号匹配。换了编号的群要自己把新编号写进去，才会继续用那份文件规则。
- 自部署和云模式都抄。云额度计数仍在内存，不跟着搬。
- 30 天保留期不动。
