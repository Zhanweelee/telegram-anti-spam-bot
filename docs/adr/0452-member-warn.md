# ADR 0452：私聊警告满三次再封禁

- 状态：已接受
- 日期：2026-11-04

## 背景

`/ban` 立刻封禁。群里有人第一次发广告时，管理员常常只想记下一次，第三次再封。次数如果写进 D1，就要新增表。警告是管理员当场处理时的计数，不是审计，也不是要保留 30 天的原文。

## 决策

- 私聊命令 `/warn <chatId> <actorId>`、`/unwarn <chatId> <actorId>`、`/warns <chatId> <actorId>`。两个 id 都要匹配 `^-?\d{1,20}$`。多出来的参数不发出请求。群聊里的同样文本不执行。
- 配置里的管理员可以操作任意群。接入目录里的人只能操作自己的群。
- 次数按 tenant、chat、actor 存在内存里。上限 128 个群、每群 64 个人。放不下时回复「参数无效」，不封禁。
- 未满 3 次只加一，回复当前次数。不调用 `banChatMember`。
- 第 3 次调用 `ModerationPort.banActor`。配了 token 时仍是 `banChatMember`，`revoke_messages` 为 false，不带 `until_date`。
- 没有封禁端口，或封禁失败时，次数退回加一之前。回复「参数无效」。
- 已经是 3 次时，再发 `/warn` 不再封禁，回复已经达到 3 次。
- `/unwarn` 把这个人的次数清掉。没有次数时回复没有警告。不调用 `unbanChatMember`。
- `/warns` 只读次数。0 次回复没有警告。
- 回复和日志不写姓名、消息原文或 token。
- 没配 DB 时，进程或 isolate 重启后次数从 0 开始。已经发出的封禁还在 Telegram 上。配了 DB 之后，次数改由 ADR 0453 放进 D1。

## 备选

| 方案 | 放弃原因 |
| --- | --- |
| 把次数放进 D1 | 要新增表。警告不是审计记录。 |
| 第 3 次顺便 `revoke_messages: true` | ADR 0004 要求封禁不隐含删除。 |
| `/unwarn` 同时解除封禁 | 清次数和放人回来是两件事。解除仍用 `/unban`。 |
| 规则自动累计警告 | 这一轮只做管理员手动计数。自动警告会改默认动作。 |

## 后果

- 管理员可以先警告两次，第三次再永久封禁。历史消息仍不由这条命令删除。
- 重启会忘掉未满 3 次的计数。封禁本身不会因此解除。
- 云额度的基础检测器名单没有改。30 天保留期没有改。
