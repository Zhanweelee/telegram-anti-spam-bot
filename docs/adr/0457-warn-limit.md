# ADR 0457：每个群可以改警告上限

- 状态：已接受
- 日期：2026-11-04

## 背景

ADR 0452 把警告上限定成 3。有的群第一次就要封，有的群想多记几次。这个数字如果散落在命令和规则动作里，改一处就会对不上。

## 决策

- 默认仍是 `WARN_LIMIT`，也就是 3。`default.json` 不改。
- 一个群可以改成 1 到 10 的整数。`MIN_WARN_LIMIT` 是 1，`MAX_WARN_LIMIT` 是 10。
- 私聊 `/warnlimit <chatId>` 只读。`/warnlimit <chatId> <limit>` 写入。`reset` 和写成 3 都删掉自定义记录，读出来仍是 3。
- 自定义记录按 tenant 和 chat 存放。内存和 D1 各有一份上限表，和次数分开。没改过的群不占记录。最多 128 个群。放不下时回复「参数无效」，原来的上限还在。
- 配了 DB 时上限在 `warn_limits`。没配时在内存，重启后回到 3。次数仍按 ADR 0453。
- 不是 1 到 10 的整数读出来按 3。D1 里坏掉的行也按 3。
- `/warn`、`/warns` 和 `createWarnAction` 都读这份上限。未满不封禁。刚写到上限时封禁，失败则退回这一次。已经达到上限时，命令不再封禁；流水线再命中会再封禁。
- 列表和单人回复里的分母是这个群的上限。
- 群号仍要匹配 `^-?\d{1,20}$`。多出来的参数回复用法。不合规则的数字回复「参数无效」。
- 配置里的管理员可以改任意群。接入目录里的人只能改自己的群。群聊里的同样文本不执行。
- 没有存储，或读写失败时，回复「参数无效」。日志是 `operator_rejected`。不写姓名、消息原文或 token。这条命令不调用 Telegram。
- 30 天保留期不改。上限不是消息原文，也不自动清。

## 备选

| 方案 | 放弃原因 |
| --- | --- |
| 把上限放进运行时 KV | 次数在 D1。上限跟次数分开放，重启后命令和流水线会对不上。 |
| 改全局常量 | 一个群想严、另一个群想松。默认仍要是 3。 |
| 允许 0 或大于 10 | 0 会让第一次警告失去意义。更大的数让 64 人的列表和封禁时机都变远。 |
| 降低上限时把已经超过的人立刻封禁 | 改配置不应该顺便封人。下一次 `/warn` 或规则命中再处理。 |

## 后果

- 没改过的群和以前一样，第 3 次封禁。
- 上限改成 1 时，第一次 `/warn` 或第一次规则 `warn` 就封禁。
- 云额度的基础检测器名单没有改。30 天保留期没有改。
