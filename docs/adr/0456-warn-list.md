# ADR 0456：私聊列出一个群的警告

- 状态：已接受
- 日期：2026-11-04

## 背景

`/warns` 只能查一个已知的人。规则动作 `warn` 会在管理员不在场时累计次数。要看这个群里还有谁被警告过，管理员得已经知道编号。

## 决策

- `WarnStore` 增加 `list(tenantId, chatId)`。每一项是 `{ actorId, count }`。
- 只列出次数大于 0 的人。次数高的在前。次数相同按编号的十进制从小到大。编号可以有 20 位，比较用 `BigInt`。
- 内存和 D1 用同一套排序。D1 先 `SELECT actor_id, count`，再在进程里排。不是编号、次数不是正整数的行跳过。
- 每群最多 64 个人，所以一则回复装得下，不再截断。
- 私聊 `/warns <chatId>` 列出这个群。第一行是群号，后面每人一行，写成 `{actorId} {count}/3`。
- 这个群没有警告时，中文回复 `{chatId} 没有警告`，英文回复 `No warnings in {chatId}`。
- `/warns <chatId> <actorId>` 仍只读一个人。多出来的参数回复用法。
- 群号或人号仍要匹配 `^-?\d{1,20}$`。不合规则回复「参数无效」。
- 配置里的管理员可以看任意群。接入目录里的人只能看自己的群，其它群回复「没有权限」。
- 群聊里的同样文本不执行。
- 没有次数存储，或 `list` 失败时，回复「参数无效」。日志是 `operator_rejected`，不带姓名、消息原文或 token。
- 这条命令不调用 Telegram。
- `WARN_LIMIT` 仍是 3。`default.json` 仍是 `delete`。30 天保留期不改，这些行不是消息原文，也不自动清。

## 备选

| 方案 | 放弃原因 |
| --- | --- |
| 回复太长就截断 | 64 个 20 位编号大约 1700 字，低于单条回复上限。截断会让人以为后面没有了。 |
| 按字符串排序 | `10` 会排在 `9` 前面。编号是十进制。 |
| 在 SQL 里按编号排序 | SQLite 的文本序同样把 `10` 放在 `9` 前面。数值转换要和内存用同一套 `BigInt`。 |
| 把上限改成可配置 | 这一轮只补上怎么看已经记下的次数。上限仍是 3。 |

## 后果

- 管理员不用先知道编号，就能看到这个群里被警告过的人。
- 和 `/warn`、`/unwarn`、规则动作 `warn` 看的是同一次数。
- 云额度的基础检测器名单没有改。30 天保留期没有改。
