# ADR 0071：比较前把 %2B 收成加号

- 状态：已接受
- 日期：2026-11-02

## 背景

ADR 0070 把 `%2F` 收成斜线。邀请路径里的加号仍可以写成 `%2B`。`https://t.me/%2B…` 能解析，主机名是 `t.me`，路径仍是 `/%2B…`。邀请正则要的是字面 `+`，所以这条只被当成公开链接放过。没有协议的 `t.me/%2B…` 同样进不了邀请。

## 决策

- `foldEncodedSeparators` 再把 `%2B` / `%2b` 收成 `+`。
- 链接检测在抽主机名前调用它。`hostFromUrl` 在 `new URL` 之前也调用它。
- `%252B` 不含这段字符，仍原样留下。
- 只影响这次比较。正文和哈希不变。证据仍只留主机名。
- 公开用户名 `t.me/durov` 仍保留。普通域名 `example.com/%2Bdocs` 仍保留。`joinchat` 路径里的 `%2B` 不是邀请码，仍放过。
- 关键词和正则仍只用 `foldMatchText`。
- 不改 ADR 0026 的基础检测器名单。不引入同形字库。

## 备选

| 方案 | 放弃原因 |
| --- | --- |
| 只改邀请正则，让它接受 `/%2B` | 按钮和正文各有一份正则，还要再处理大小写。两层编码 `%252B` 更容易被误收。 |
| 整段 `decodeURIComponent` | `%20`、`%2E` 和其它序列会一起展开。这和 ADR 0067 的边界冲突。 |
| 放进关键词折叠 | 加号不是格式字符。关键词不该因为 `%2B` 改变比较。 |

## 后果

- `t.me/%2B…`、`telegram.me/%2b…` 和按钮上的 `https://t.me/%2B…` 会记成邀请。
- `t.me/durov`、`example.com/%2Bdocs`、`joinchat/%2B…` 和 `t.me/%252B…` 仍放过。
- 邀请码不进事件。直接调用 `extractHosts` 的代码仍扫描原字符串。
