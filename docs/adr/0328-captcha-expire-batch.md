# ADR 0328：到期挑战按批写入和删除

- 状态：已接受
- 日期：2026-11-04

## 背景

Cron 一次最多列出 64 条到期挑战。原来每条先 `DELETE` 再 `INSERT` 审计。免费计划每次调用最多 50 次 D1 查询。冷启动还要先跑 4 条建表语句。64 条还没处理完，这次调用就会失败。

删除已经发出、审计还没写上时，这行挑战不会再出现。下一次 Cron 补不上审计。

`db.batch()` 整批只算 1 次查询。一批里的语句在同一个事务里，一条失败就全部回滚。2026-11-04 核对过 [D1 limits](https://developers.cloudflare.com/d1/platform/limits/)。

## 决策

- `Storage.putAuditsIfAbsent` 按 `(tenantId, chatId, eventId)` 补上还没有的审计。已经存在的主键留着，不再插一行。
- `CaptchaStore.deleteMany` 一次删掉给出的挑战。空列表不发查询。
- `expireChallenges` 先写入这批评测审计，再 `deleteMany`。删除失败时挑战还在，下一次 Cron 会再补审计并重试删除。
- D1 把这两次调用各打成一个 `batch()`。一次仍最多 64 条。不调用 `releaseActor`。
- 单条按钮超时仍写同一份审计再删自己的挑战。普通 `appendAudit` 仍是插入，主键冲突不会被悄悄丢掉。
- 不改 ADR 0026，也不做 30 天清理。

## 备选

| 方案 | 放弃原因 |
| --- | --- |
| 把 64 改成 20，继续一条一条查 | 能躲开 50 次上限，但每条仍是两次往返。删除和审计之间失败时，审计还是会丢。 |
| 先删再写 | 删除成功、写入失败时，挑战已经不在，下一次 Cron 看不到它。 |
| 在 core 里循环调用 `batch` | core 不认识 D1。批量端口留给适配器决定怎么发。 |

## 后果

- 每个 `Storage` 和 `CaptchaStore` 都要实现新方法，并继续跑原来的契约。
- 配了 `DB` 的 Cron 在列出到期行之后，再用两次批量查询完成 64 条。建表语句仍是逐条执行。
- 没配 `DB` 时仍在内存里逐条补审计和删除。重复的主键不追加。
- 超过 64 条时，剩下的等下一次 Cron。Telegram 的 `until_date` 仍会自己到期。
