# ADR 0166：接不上的用户信息前停住的主机名也留下

- 状态：已接受
- 日期：2026-11-02

## 背景

Android `LinkifyPort.WEB_URL` 会先尝试把 `@` 前面的一段当成用户信息。后面能接上主机名、路径、收得住的端口、`_`，或者字符串到此结束时，用户信息成立，打开的是 `@` 后面的主机名。

`http://bit.ly@.evil.com`、`http://bit.ly@!` 和 `http://203.0.113.133@.evil.com` 接不上。正则退回，打开的是 `@` 前面的 `bit.ly` 或裸 IP。整段按用户信息解析时，主机名变成点开头的尾巴，对不上短链或裸 IP。`http://bit.ly@example.com`、`http://bit.ly@/path` 和 `http://bit.ly@:80/path` 的用户信息仍然成立。

## 决策

- 用户信息只有在 `@` 后面能接上时才算进去。接不上时，按没有这段用户信息来切高亮，留下 `@` 前面的主机名。
- 切出来的主机名走现有的裸 IP、短链和 denylist 判断。只拆一层。最多 8 个。证据只留主机名。
- 邀请仍按原来的整段地址读取。接不上的 `@` 后面的路径不改记成邀请。
- 已经写在 `text_link`、按钮或其它结构化字段里的地址整段打开。
- 不新增检测器。不改 ADR 0026 的基础检测器名单。

## 备选

| 方案 | 放弃原因 |
| --- | --- |
| 只要出现 `@` 就把前面当成用户信息 | `bit.ly@.…` 打开的是前面的短链或裸 IP。 |
| `@` 一律从主机名里拿掉 | `bit.ly@example.com` 和 `user:pass@bit.ly` 会记错主机名。 |
| 接不上之后的路径改记成邀请 | `t.me@.…/+邀请码` 打开的是没有这段路径的主机名。 |

## 后果

- `http://bit.ly@.…` 和 `http://203.0.113.133@.…` 按现有短链或裸 IP 规则删除。证据仍只有主机名。
- `http://bit.ly@example.com`、`http://bit.ly@/…`、`http://bit.ly@:80/…`、`http://bit.ly@` 和 `http://bit.ly@_…` 留着。`http://example.com@.…` 留着。
- `https://t.me@.…/+…` 不改记成邀请。路径不进证据。
