# ADR 0038：私聊 `/rules` 列出正在执行的规则

- 状态：已接受
- 日期：2026-11-01

## 背景

ADR 0019 让检测在订阅之后走 `resolveRuleSet`。ADR 0034 的 `/rules` 仍调用 `loadRuleSet`，只列出文件规则。订阅留在 `POLICY_KV` 之后，管理员重启仍记得包 id，却在 `/rules` 里看到另一份规则。

## 决策

- `/rules` 改为调用 `resolveRuleSet`。命令拿到规则包来源和归档，并且这个群有订阅时，列出的就是检测会用的那一份，包括套上的规则开关。
- 没传来源或归档时，行为与以前相同，只列文件规则。例子和旧调用不用一次改完。
- 订阅存储抛错时回复 `参数无效`，日志是 `pack_store_failed`，不写异常文本。这和检测把读失败当成未订阅不同：命令如果仍列出文件规则，管理员会以为已经退订。
- 规则包刷新失败时，`/rules` 和检测一样：有上一份就列上一份，没有才列本地规则。日志仍是 `pack_update_failed`。
- `/rule` 仍按文件规则校验 id。规则包是共享文档，不在这条命令里改。包里没有的 id 可以先记着，退订后再生效。见 ADR 0034。
- `/rules` 不做额度降级。降级是检测当时的过滤，不是这份规则的启用状态。

## 备选

| 方案 | 放弃原因 |
| --- | --- |
| `/rules` 继续只列文件规则 | 订阅已经能在重启后留下。管理员看到的和检测执行的不是同一份。 |
| 读订阅失败时列文件规则 | 和检测的 fail-open 一样，但会让人以为这个群没有订阅。 |
| `/rule` 改为按规则包校验 id | 包是共享的。单群开关仍要对着文件底稿，退订后才生效。 |

## 后果

- 传入规则包来源时，`/rules` 和检测看到同一份解析结果。标题里的 pack id 见 ADR 0039。
- Worker 把现有的来源和归档传给命令。没配 `POLICY_KV` 时订阅仍在内存，列出的内容一样。
- 另一个 isolate 的订阅最多晚 60 秒，`/rules` 也是这样。
