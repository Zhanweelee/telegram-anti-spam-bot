# ADR 0638：入群申请的申请人画出的全名只留主机名

- 状态：已接受
- 日期：2026-11-06

## 背景

管理员看入群申请时，名单和申请页把申请人画成一行名字。Android 的 `MemberRequestCell` 用 `UserObject.getUserName`。申请页的 `JoinSheetUserCell` 用 `ContactsController.formatName`。两边都是名和姓先去掉两端空白，名在前，姓接在后面。名去掉空白后是空的，就只画姓。空格后面仍画。用户名不在这行里。批准人那一行用的是名，Bot API 的 `chat_join_request` 上没有这个人。

Bot API 把申请人放在 `chat_join_request.from`。见 ADR 0607。当时名的长度大于 0 就丢掉姓。空白也算有名。短链可以只写在姓上。把整段收成简介会改变简介哈希，关键词也会命中名字。群名和邀请链接仍是管理员自己的，不该因为它们拒绝申请。

## 决策

- 只在 `kind: "join_request"` 上，从 `from` 会画出来的全名留主机名。`from` 必须能取出用户编号。
- 名和姓都先去掉两端空白。两边都还有字时，名在前、姓在后，中间一个空格。名去掉空白后是空的，且姓去掉空白后还有字时，只读姓。两边都空时不读。空格不截断。用户名不读。
- 主机名仍记在 `nameHosts`。邀请仍记在 `nameInvites`。没有主机名就不设这两个字段。简介仍只来自 `bio`。名字不进 `profile`，也不改简介的哈希。
- 已有链接检测器先看简介，再看这份主机名。简介里已有短链时，证据仍先记简介的主机名。关键词和默认正则仍只看简介，不命中这个名字。
- 群名、邀请链接、`user_chat_id` 和查询号原文不读。布尔值的 `from` 仍让这条更新被忽略。
- 不新增检测器，不新增命令。菜单仍是 99 条。不改 ADR 0026 的基础检测器名单。`join_request` 仍默认打开，动作仍是拒绝。8 个主机名的上限不变。不调用 `approveChatJoinRequest`。

## 备选

| 方案 | 放弃原因 |
| --- | --- |
| 继续只读名 | 名单和申请页把姓画在同一行里。姓上的短链会留在申请上。 |
| 把名字拼进简介 | 关键词会命中人名，简介哈希也会变。见 ADR 0116。 |
| 连邀请链接和群名一起读 | 正常的 `t.me` 邀请和群名会被拒绝。见 ADR 0116。 |
| 新命令 `/requestname` | 菜单只剩一个空位。现有 `links` 已经能拒绝短链。 |

## 后果

- 申请人的全名里出现短链、邀请或裸 IP 时，这条申请会被拒绝。证据只有主机名。人还没进群。
- 全名原文、路径和用户名不进事件。简介哈希不变。关键词不命中全名。
- 空白名不挡住姓。空格后面的网址仍读。
- 简介里已有短链时，证据仍先记简介的主机名。
- `example.com` 和公开的 `t.me/名字` 留下。没有短链的姓名仍留给管理员。带查询号时仍按原来的方式答复。
- 群名、邀请链接和用户编号仍不读。布尔值的 `from` 仍忽略。真正入群后的昵称仍按 ADR 0117。管理员仍豁免。云额度的基础检测器名单没有改。30 天保留期没有改。
