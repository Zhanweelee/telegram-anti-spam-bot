# ADR 0170：主机名后面的标点再打开的主机名也留下

- 状态：已接受
- 日期：2026-11-02

## 背景

Android `LinkifyPort.WEB_URL` 先读用户信息，再读主机名、一到五位数字端口，最后才在 `/` 或 `?` 处开始路径。`! # $ & ( ) * + , ; = ~` 以及不是端口的 `:` 可以出现在路径里，但写在主机名紧后面、路径还没开始时会结束当前匹配。后面如果还有网址，会再打开一次。

`http://example.com!http://bit.ly/…` 因此会打开 `bit.ly`。整段当成一个地址时，主机名只剩 `example.com`。`#` 同样结束匹配，不开始路径。斜杠或问号后面的同一批标点仍属于前一个路径。

`user:pass@bit.ly`、`bit.ly@example.com`、`bit.ly@/…` 和 `bit.ly@:80/…` 是接得上的用户信息，仍是一段。

## 决策

- 带协议的一段先试以 `@` 结尾的用户信息，字符集跟 Android 的用户信息一致。用户信息后面的主机名可以为空，再接可选路径。没有用户信息时，主机名至少要有一个字符。
- 主机名收 ASCII 字母数字、`.`、`_`、`-`、完整的 `%HH`，以及不是 JavaScript 空白、也不是路径类漏掉的码位的非 ASCII 标签字符。后几个平面的标签字符对仍留在这一段里。
- 主机名后面可以接一到五位数字端口，且后面不能再是数字。路径只从 `/` 或 `?` 开始。`#` 不开始路径。
- 路径里能出现、但主机名结构用不上的标点，在路径还没开始时结束这一段。后面的网址按自己的一段来抽主机名。路径已经开始之后，这些标点留在这一段里。
- 每段仍走现有的裸 IP、短链、邀请和 denylist 判断。只拆一层。最多 8 个。证据只留主机名。
- 切开之后单独的邀请地址仍按邀请读取。同一段里被这个标点挡住的路径不改记成邀请。
- 已经写在 `text_link`、按钮或其它结构化字段里的地址整段打开。
- 不新增检测器。不改 ADR 0026 的基础检测器名单。

## 备选

| 方案 | 放弃原因 |
| --- | --- |
| 整段只留第一个主机名 | 主机名后面的标点再打开的短链和裸 IP 点得开。 |
| 这些标点在路径里也切开 | `example.com/!http://bit.ly` 仍是一个网址。 |
| `@` 一律结束主机名 | 接得上的用户信息，以及 `@` 后面直接是路径的空主机名，都会被拆错。 |

## 后果

- `http://example.com!http://bit.ly/…`、`http://example.com#http://t.co/…` 和 `http://news.example:http://203.0.113.137/…` 按现有短链或裸 IP 规则删除。证据仍只有主机名。
- `http://example.com/!http://bit.ly/…` 和 `http://example.com/?http://bit.ly/…` 留着。
- `http://user:pass@bit.ly/…` 仍按短链删除。`http://bit.ly@example.com` 留着。
- `https://t.me!/+…` 不记成邀请。`http://example.com!https://t.me/+…` 按邀请删除。路径不进证据。
- 裸域名和 `www.` 在最后一个标签处结束，后面 Android 另外打开的主机名也留下。见 ADR 0171。
