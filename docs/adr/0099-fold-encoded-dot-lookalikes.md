# ADR 0099：其余间隔号的一层编码在比较前收成间隔号

- 状态：已接受
- 日期：2026-11-02

## 背景

ADR 0098 只收了 `%C2%B7`。同一组间隔号的其它 UTF-8 编码仍看不见。`bit%E3%83%BBly` 会被 URL 解析器收成 punycode，短链名单对不上。带协议的全角句点 `%EF%BC%8E` 有时已经会被解析器收成点，没有协议时仍抽不出来。

句号 `。` 的编码 `%E3%80%82` 不在这一组里。第二层仍留下。

## 决策

- `foldEncodedMiddleDot` 现在收 ADR 0093 的全部间隔号：`U+00B7`、`U+2022`、`U+2027`、`U+2219`、`U+22C5`、`U+30FB`、`U+FF0E`、`U+FE52`、`U+FF61`。
- 只收一层 `%HH` 连写的 UTF-8。大小写都认。收成原来的字符，再走 ADR 0093 的删除或收成 `.`。
- `%E3%80%82` 和第二层 `%25HH` 保留。
- 关键词、正则、链接检测、`hostFromUrl` 和从正文里抽网址的扫描沿用同一层。
- 事件里的正文和 `textSha256` 不变。不新增检测器，也不改 ADR 0026 的基础检测器名单。

## 备选

| 方案 | 放弃原因 |
| --- | --- |
| 连 `%E3%80%82` 一起收 | 那是句号 `。`。没有协议时不应把它变成点。 |
| 连第二层一起收 | `%25C2%25B7` 和 `%252E` 都留下。这一项保持同一条线。 |
| 只在链接检测里收 | `加%E3%83%BB微信` 仍对不上关键词。 |

## 后果

- `bit%E3%83%BBly/…` 和 `t%EF%BC%8Eme/+…` 会走现有短链和邀请规则。`example%E3%83%BBcom` 仍保留。
- `加%E3%83%BB微信` 会命中关键词 `加微信` 和默认正则。
- `example%E3%80%82com` 和 `bit%25E3%2583%25BBly` 仍抽不出来。
- 重复计数仍按原文哈希。
