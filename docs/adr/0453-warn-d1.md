# ADR 0453：配了数据库时把警告次数放进 D1

- 状态：已接受
- 日期：2026-11-04

## 背景

ADR 0452 把警告次数放在 isolate 内存里。Cloudflare 上连续两次 `/warn` 可能落到不同 isolate。第二次从 0 开始，第 3 次封禁对不上。验证挑战在配了 `DB` 时已经进 D1。警告次数是同一个问题，只是一行整数。

## 决策

- 配了 `DB` 时，`WarnStore` 使用 `warn_counts`。主键是 `(tenant_id, chat_id, actor_id)`，列只有 `count`。不存姓名、消息原文或时间。
- 表加进现有的 `storageMigrationStatements`，语句是 `CREATE TABLE IF NOT EXISTS`。不改 `audits`、`rule_sets`、`review_samples` 或 `captcha_challenges`。
- 加一用一条 `INSERT ... ON CONFLICT DO UPDATE`。另一个 store 对象读同一份库，看到同一次数。
- 上限仍是 128 个群、每群 64 个人。放不下时抛出 `WarnCapacityError`，命令回复「参数无效」，不封禁。
- 没配 `DB` 时仍用内存实现。重启后从 0 开始。
- `/warn`、`/unwarn`、`/warns` 的回复和封禁参数不改。封禁失败时仍把次数退回。
- `/unwarn` 删除这一行。不调用 `unbanChatMember`。

## 备选

| 方案 | 放弃原因 |
| --- | --- |
| 继续只放内存 | 两次警告可能不在同一个 isolate，次数永远到不了 3。 |
| 放到 KV | 警告是按人读写的小整数。D1 已经承担验证挑战，同一条绑定即可。 |
| 给每一行加创建时间并纳入 30 天清理 | 这一行不是消息原文，也不是审计。保留期不在这一轮改。 |

## 后果

- 配了 `DB` 的部署里，警告次数在 isolate 之间保持。
- 冷 isolate 的第一笔存储调用会多执行一条建表语句。
- 每次警告是一次 D1 写。管理员命令不是检测热路径。
- 云额度的基础检测器名单没有改。30 天保留期没有改。
