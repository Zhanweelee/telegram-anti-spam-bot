# ADR 0339：同一更新只计一次 webhook 预算

- 状态：已接受
- 日期：2026-11-04

## 背景

Webhook 预算在流水线之前按群计数。10 秒内超过 30 条就返回 200，不再检测。ADR 0024 数的是更新。Telegram 重试同一个 update 时，事件 id 不变。同一次投递落到这个 isolate，会把 30 条名额再占一次。

ADR 0338 让洪泛窗口认得事件 id。预算调用 `observe` 时还没有把 id 传进去。

## 决策

- `allow` 可以带 `eventId`。Worker 把事件 id 传进去。
- 计数仍走现有内存窗口。同一个群里，这个 id 已经在最近 32 个有效 id 中出现过，就不再占名额，并按当前条数决定放行或丢掉。
- id 的字符限制与洪泛窗口相同。其它值照旧每次都计。没传 id 的调用仍每次加 1。
- 上限仍是 30。窗口仍是 10 秒。不写 KV 或 D1。

## 备选

| 方案 | 放弃原因 |
| --- | --- |
| 记住这一窗口的全部事件 id | 重试只发生在刚处理过的几条里。窗口本身最多 32 个样本。 |
| 把已计 id 写进 KV 或 D1 | ADR 0024 拒绝为这次闸门再写存储。 |
| 改掉 30 或 10 秒 | 这次只避免同一次投递占两个名额。 |

## 后果

- 同一个 isolate 上的重试不再把一个群提前打进 `limited`。
- 落到另一个 isolate 的重试仍会计一次。那边的计数本来就是另一份内存。
- 名额已经超过 30 之后，重试一条更早的更新也会拿到 `limited`。第一次如果没跑完，这次也不会补跑。
- 样本过期后，记住的 id 不占新名额。当前条数不超过 30 时，这次重试仍会检测。
- 30 天保留期不动。这仍不是每群云额度。
