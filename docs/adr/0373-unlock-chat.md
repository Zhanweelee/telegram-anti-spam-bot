# ADR 0373：私聊可以打开群的默认发言权限

- 状态：已接受
- 日期：2026-11-04

## 背景

`/lock` 用 `setChatPermissions` 把十六项默认权限都关掉。官方方法没有到期时间，关掉之后会一直保持。管理员如果还要打开，只能回到 Telegram 客户端。

`/lock` 没有保存锁定前的权限。全开会超过群里原来更窄的默认值。ADR 0372 把这件事留到单独决定。

没有 token 时，内存适配器可以把一次打开记下来。私聊如果复用这次成功，回复会写成群已经可以发言。

## 决策

- 私聊命令 `/unlock <chatId>`。群 id 匹配 `^-?\d{1,20}$`。群聊里的同样文本不执行。
- 配置中的管理员可以操作任意群。接入目录里的人只能操作自己的群。
- 命令调用 `ModerationPort.unlockChat`，只带 tenant 和 chat。适配器调用 `setChatPermissions`。权限与单人解除禁言相同的十六项，全部为 true，并带上 `use_independent_chat_permissions: true`。不带成员号，也不带 `until_date`。
- 回复写明：这可能比锁定前更宽，单人禁言仍在。
- 不读取成员名单，也不逐个调用 `restrictChatMember`。已经单独禁言的人保持各自的限制。不读取或恢复一份锁定前的权限快照。
- 没有 token、没有这个方法，或调用失败时回复「参数无效」。日志只写 `operator_rejected`，带上 eventId、chatId 和命令名。不写异常文本或 token。
- 没有 token 的 Worker 不把内存里的记录回复成已经成功。
- 不修改黑名单、白名单、用户封禁或单人禁言。

## 备选

| 方案 | 放弃原因 |
| --- | --- |
| 恢复锁定前的默认权限 | `/lock` 没有保存那份权限。无法知道原来开了哪些项。 |
| 不带 `use_independent_chat_permissions` | 权限隐含可能和这次显式打开的十六项不一致。 |
| 回复写成与锁定前相同 | 全开可能比原来更宽。管理员会以为只是还原。 |
| 没有 token 时也回复「已打开」 | 群里的默认权限可能还是关闭的。管理员会以为已经放开。 |

## 后果

- 成功只表示 Telegram 接受了这一次 `setChatPermissions`。频道，或 bot 缺少 `can_restrict_members` 时，回复是「参数无效」。
- 默认权限变成十六项全开。这可能比锁定前更宽。单人禁言和封禁不变。
- 一次打开是一次 Telegram 子请求。
- 30 天保留期不动。
