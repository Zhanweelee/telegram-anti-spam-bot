# ADR 0105：旁路纯文本走和正文相同的主机折叠

- 状态：已接受
- 日期：2026-11-02

## 背景

链接检测器在读正文前会去掉零宽字符，并把 `%2E`、`%2F`、`%2B` 和一层 `%HH` 收成字符。按钮文字、文件名、作者签名和其它旁路纯文本只做了字形折叠，停在抽主机名的正则之前。

已有别的正文时，这些字段不并进正文。零宽空格拆开的 `bit.ly`、`b%69t.ly` 和 `t.me%2F+…` 只出现在按钮文字里时，短链和邀请都对不上。

带协议的按钮地址走 URL 解析。那一层把百分号编码的格式字符放在最里面。这次不改那个顺序。

## 决策

- 导出 `foldHostScan`。顺序与链接检测器读正文相同：西里尔形近字、全角拉丁字母、夹在标签里的字母、一层间隔号编码、点状间隔号、正文折叠、两层格式字符、`%2E` / `%2F` / `%2B`、一层字母表、括号点。
- 链接检测器和旁路纯文本都调用它。
- 带协议的地址仍按原来的顺序解析。
- 关键词和正则不调用它。
- 普通空格和第二层百分号编码留下。
- 事件里的正文和 `textSha256` 不变。不新增检测器，也不改 ADR 0026 的基础检测器名单。

## 备选

| 方案 | 放弃原因 |
| --- | --- |
| 让带协议的地址也改成这个顺序 | 那一层已经先去掉编码过的格式字符，再交给 URL 解析。现有测试钉住了这个顺序。 |
| 连第二层括号点一起收 | ADR 0104 已经留下第二层。 |
| 再去掉一种文字 | 更宽的同形字会带来更多误伤。 |

## 后果

- 已有正文时，按钮文字里用零宽空格拆开的 `bit.ly`、`b%69t.ly` 和 `t.me%2F+…` 走现有短链和邀请规则。路径和邀请码不进事件。
- `bit. ly` 仍抽不出来。
- 第二层 `%255B.%255D` 仍留下。
- 带协议的地址解析顺序不变。
- 重复计数仍按原文哈希。
